# 任務遂行プロトコル（全モデル共通・常駐）

どのモデル（Sonnet / Opus / その他）がこのプロジェクトで作業しても同じ品質に着地させるための約束。
**知能はモデルではなくシステムに置く**: 自由記述より構造化データ、手書きより生成器、感想より検証スクリプト。

## 1. 任務の型（これが無い作業は始めない）
すべての定常任務は次の3点セットを持つ。無い任務を振られたら、**先に3点セットを作ってから**本体に着手する。
1. **入口**: 1コマンド or 1ドキュメント（例: 曲記事 = CLAUDE.md記事作成フロー）
2. **Definition of Done**: 機械検証スクリプトが全✅（例: `node agent/src/check-article.mjs {slug}`）
3. **出口**: review push → `notify-review.mjs` → ユーザー承認 → `/publish`

「たぶん大丈夫」「目視で確認した」はDoneではない。**検証スクリプトのexit 0だけがDone。**

## 2. 着手前
- CLAUDE.mdの該当セクションと、そこが指す docs（fact-check-rules / article-tone / column-split-rules）を読む
- 読んだ内容の要約をレスポンスに書かない。すぐ実行する
- 不明な事実は推測せずWebSearch/一次ソースで裏取り。**IDや数値を推測で書いた時点で任務失敗**

## 3. 文章は三稿制（初稿→他人の目→仕上げ）
日本語の記事本文（曲ページ・コラム）は必ず3パスで作る。
1. **初稿**: article-tone.mdチェックリストに従い一気に書く
2. **第三者レビュー**: `node agent/src/check-tone-only.mjs {slug}` で機械検査を先に通し、その後
   「**これは外注ライターがAIで書いた文に見えないか？**」の一点で自分の文を他人として再読する。
   見るのは: 評論家ヅラの断定、同じ文末の連打、熱のない要約文、専門語の放置、事実の言い切りに裏取りがあるか。
   違反箇所は列挙せずその場で直す（歌詞英語行をレスポンスに出さない）
3. **仕上げ**: 直した後に check-tone-only を再実行 → check-article.mjs へ

## 4. 内部リンクは書かない（生成させる）
- 関連記事リンクは **SongLayout が songs.ts から自動生成**する（同アーティスト→同プロデューサー→同じ元ネタ→同時代×同地域）。
  曲・アーティストが増えれば**リンクは勝手に増える**。手で追いかけない
- **`.astro` 本文に手書きの「関連記事」カードセクションを新設しない**（腐ってデッドリンク化した前例あり。レイアウトに任せる）
- 本文の文中リンク（コラムへの言及・スラング詳細）は歓迎。ただしリンク先の実在を `check-internal-links.mjs` が最終検証する
- コラム⇔曲の紐付けは `columns.ts` の `relatedSongs` に登録する（これも両方向に自動描画される）

## 5. 失敗は2回目でコード化（再発防止の掟）
同じ種類の指摘・事故が**2回目**に出たら、その修正だけで終わらせず、**その場で仕組み化までを任務に含める**:
- 文体系 → `docs/article-tone.md` に追記＋可能なら `tone-rules.mjs` の検出語に追加
- 事実系 → `docs/fact-check-rules.md` に追記
- 構造系（リンク切れ・コミット漏れ・ID誤り等） → 検証スクリプトに検出項目を追加
仕組み化コードがcommitされて初めてその任務は完了。**これがこのプロジェクトの品質が上がり続ける唯一のメカニズム。**

## 6. 禁止事項（絶対）
- `git add .` / mainへの直push（インフラ・docs除く） / `--no-verify` でのガードバイパス
- 歌詞英語行・歌詞HTMLのレスポンス出力（CLAUDE.mdコンテンツフィルター回避ルール）
- 存在しないslug・YouTube ID・コラムへのリンク記述（検証前に書くのは可。検証せず完了報告は不可）
- ❌が残った状態での「完了しました」報告。詰まったら偽装せず「どこで詰まったか」を報告する
